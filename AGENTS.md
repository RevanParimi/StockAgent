# StockAgent repository working instructions

## The goal

The owner judges this product by one thing: investments turning into profits, visible on the product (owner, 6 and 14 Nov 2026). The portfolio is paper money. Before starting a story, name the step of the profit path it serves: invest, hold, sell or measure. A story that serves none of them waits unless the owner asks for it. The learning rebuild is off the plan and the factor engine is paused (STATE scope `removed` and `paused`); adaptive learning stays observe-only. The dated review behind these priorities is `docs/audit/2026-11-14-profit-path-architecture-review.md`. The path from "it invests" to "it beats a professional, and can prove it" is `docs/planning/PI-2026-09/EDGE-ROADMAP.md`: read it before any story it lists, check its "what already exists" table before building, and at each results review ask the owner which paused stories to promote.

## Continuing the active PI

When the user says **continue** (or asks to work through the audit sprint plan), use repository state rather than assuming hidden chat memory:

1. Read the current handoff (the first `#` section of `docs/planning/PI-2026-09/HANDOFF.md`, and the standing rules that open its "START HERE" checklist) and, in `docs/planning/PI-2026-09/STATE.json`, the top-level fields, the pending production checks and the selected task. Read older handoff sections and archive files only when a story points there. Inspect git status and preserve unrelated user changes.
2. Resume the active story if one is in progress, changes-requested or awaiting review. Otherwise select the first `todo` story of scope `planned` whose dependencies are `done`, ordered by the state file. Treat `next_task` as a checked hint, not permission to ignore dependencies. A blocked task needs a concrete recorded reason; another ready authorized task may proceed. Stretch, paused and removed stories require the owner's explicit promotion.
3. Read only the selected story, required evidence receipt and relevant code/docs. Consult the dated audit for its linked findings; do not load every story or historical chat.
4. Execute **one phase per conversation**. A story's lane decides its phases (owner's rule, 14 Nov 2026):
   - **Decision path:** a change to what is bought, sold or sized, to how a forecast or an exit is graded, to the ledger's money arithmetic, or to who can read or change an account's data. Implementation includes appropriate tests and self-review, then stops at `review_required`. The next fresh conversation performs the hard review from `REVIEW.md`. Same-conversation self-review cannot be signed off as a fresh review; leave that gate pending and explain the fresh-chat handoff.
   - **Light:** reports, screens, briefs, documents, operations, housekeeping, and rollout stories that change one setting the owner has authorized. Implementation, tests, self-review and the full suite happen in one conversation, and the story is accepted there when the suite and the project guards pass. Its receipt says "accepted without a fresh-session review".
   - The implementing conversation names the lane and the reason in the receipt. In doubt, it is the decision path. The owner may ask for a fresh review of any story.
5. Before editing, set `active_task` and status. After the phase, update STATE.json, HANDOFF.md and the story's sanitized evidence receipt together. Record exact tests, changed-file manifest and reviewed diff/revision digest. Only accepted tested work becomes `done`; production verification is separate. Select the next ready story after acceptance, but do not start it in the same conversation.

If the user explicitly changes scope or requests a specific task, their instruction wins; record the resequencing and unresolved dependencies. If these plan files are unavailable, report that concrete problem rather than inventing completion history. No autonomous creation of new chats is available; the user opens a fresh conversation in this same repository for each phase.

## Review and change boundaries

- Update affected living documentation and human testing cases with each implementation story. Regenerate `docs/StockAgent-Three-Loops.pdf` whenever its source `docs/TECHNICAL_DESIGN.md` changes. Keep current code, planned PI behavior and measured production evidence distinct; SA-031 is the final consistency check, not a deferral of documentation to the end.
- Follow `docs/planning/PI-2026-09/REVIEW.md`. Financial targets, issue-time information, price identity/freshness, idempotency and final weight constraints require independent invariant tests, not only implementation-shaped assertions.
- Distinguish code inspection, local reproduction, measured production evidence and inference. Do not equate changed weights, retrospective replay, successful HTTP/LLM calls or code completion with demonstrated learning benefit.
- Keep tasks focused. Prefer correcting contracts and deleting measured duplication to new frameworks, distributed infrastructure or more adaptive modifiers.
- Small findings go to the backlog list, not to new stories. A finding that is low, latent or pre-existing, and changes no buy, sell, size or grade today, is one entry in `docs/planning/PI-2026-09/BACKLOG.md` with the trigger that would promote it. It becomes a story when that trigger is seen in production or the owner promotes it. Medium or higher findings on the decision path still become stories, and each says what it costs the owner in money or in a wrong decision, with an example.
- Local implementation, reversible fixes and read-only production inspection are in scope when continuing a selected story. Do not deploy, push, change production variables/flags, trigger jobs, migrate production data, or send email/push messages without applicable explicit authorization. Use prior authorization when present; prepare concrete reviewable changes before asking for missing authorization.
- Never expose `.env`, tokens, private user payloads or raw production logs in tool output/commits. Use isolated deterministic tests without real transports or runtime data. Preserve unrelated files, including the pre-existing untracked PDF.
- Keep raw diagnostics under ignored `analysis_data/`; only sanitized evidence summaries belong in tracked documentation. Do not assume those local diagnostics exist in another checkout.

The dated audit is `docs/audit/2026-09-10-repository-production-review.md`; the profit-path review of 14 Nov 2026 sets the current priorities. Historical August specifications are context, not proof of current implementation or permission for production actions.
