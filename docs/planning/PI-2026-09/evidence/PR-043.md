### The decision: stop, and the owner chooses

The card's step 1: "If dates or the full result list do not come back, stop and say so in the
receipt and the summary: the owner chooses between an Exa account of its own (dates and filters)
and stopping. A result without a date cannot be tested against the decision day." The full list
comes back; the date does not. So step 2 is not built, and PR-043 is `blocked` on the owner's
choice:

- **A. An Exa account of its own** (recommended). Exa's own API is the documented route to a
  publish date and a start-date filter, so the read's test, "published in the 30 days before the
  decision", is exact. The owner signs up, reads Exa's price list there, and puts the key into
  Railway (or says to). The next session then builds step 2 against Exa's API; the rest of the
  card stands.
- **B. Through OpenRouter as probed,** with each item dated by its URL or excerpt and an undated
  item counted as not new. This changes the read's rule, which the owner fixed; it can only
  undercount what Exa adds, since 42 of 100 items here had no date.
- **C. Stop PR-043.** PR-044 waits on it and stops with it.

Why A: the read's whole question is whether Exa finds material, recent items that Serper's five
miss. With B, almost half the items would be judged by a guessed date or by none.

### What was built

1. **The bundle keeps the company search** (`bundle_builder.py`): `_fetch_company_news` takes an
   optional `capture`; `fetch_news_result` (`news.py`) takes an optional `searches` list and
   appends each query's raw results to it. The bundle's new `company_search` field (query,
   source, Serper's raw results) is not rendered by `to_prompt_text`; the section text is the
   same with and without the capture (tested).
2. **The hook** (`base_orchestrator.py`, `_shadow_company_search`): after `_record_data_health`,
   only when the analyst produced outputs (a failed analysis is no decision). It calls
   `submit_shadow` and never raises. Every deep dive and every daily review of a held stock
   (`_run_todays_agent_scores` → `analyse` → `_run_agents` → `_run_unified`), sync and async,
   goes through this one path; so do member-requested analyses, within the budget.
3. **The shadow** (`services/data/fetchers/search_shadow.py`, new): `submit_shadow` queues the
   job and returns (one daemon thread, a queue of at most 500; a full queue drops the row with a
   warning). The job sends the query to each engine in `search_shadow.engines` through
   OpenRouter's server tool (`search_web`: the bulk model, "run exactly one web search", 10
   results, `max_tokens` 300), reads each unique result link once for its date
   (`read_page_date`, five at a time, 12 s, the first 400 KB), and appends one row to
   `data/logs/search_shadow.jsonl`.
4. **Dates, the card's order:** page metadata (published wins over modified; meta tags in either
   attribute order and JSON-LD), a date in the URL (not inside a longer number), an NSE filing
   name: strong. A month in the path (`YYYY-MM`) and `Last-Modified`: weak. The excerpt's first
   date: `excerpt_date`, beside. A refusal (4xx/5xx), a time-out or a refused address leaves
   the page unread; a URL date still counts, as in the tested method above.
5. **Only public pages:** http(s) only; every address the host resolves to must be global;
   redirects are followed by hand, at most 3, each hop checked again.
6. **Budget:** `search_shadow.weekly_budget: 200` calls a week per engine, counted in
   `data/logs/search_shadow_budget.json` under a file lock (two Uvicorn workers), the week
   from Saturday 00:00 IST. Past it the engine's entry reads `budget` and no call is made.
7. **Switch:** `search_shadow.enabled: true` (env `SEARCH_SHADOW_ENABLED`); `false` is the
   rollback. `engines: [{engine: parallel, mode: fast}, {engine: exa}]`. Without an OpenRouter
   key nothing is queued, which keeps the test suite off the network.
8. **Living documents:** KT section 3 (the switch; both files) and section 4 (a "Search shadow"
   subsection with an example); CODEBASE's module table; guide case 02-P.

### Decisions taken in this phase

- **The week starts on Saturday 00:00 IST,** so the 12:30 Saturday deep dives (the invest
  decisions) are recorded first; at about 20-40 held stocks a weekday, the daily reviews take
  the rest.
- **One row per analysis that produced outputs;** a failed analysis is no decision.
- **A daemon worker, not a thread pool:** the interpreter waits for a pool's queued jobs at
  exit, so a redeploy could have waited on the shadow.
- **The winner rule for `PR-043-W2`, fixed before any data** (card): of the engines that pass,
  the higher share is kept; within 5 points of each other, the cheaper one (Parallel `fast`).
- **PR-044's title** names "the kept engine" instead of Exa.

### Findings (self-review)

- **Fixed in the phase:** the first draft queued on a thread pool; Python waits for a pool's
  queued jobs at exit, so a redeploy could have waited minutes on queued shadow rows. Now one
  daemon thread with a bounded queue (tested).
- **Fixed in the phase:** SA-010's test drives `_run_unified` on a stand-in object; it now stubs
  the new `_shadow_company_search` as it stubs `_record_data_health`.
- **Read of the card:** "A refusal or time-out leaves the result undated" is read as the tested
  method did: the page's own dates are not read, and a date in the URL still counts (it does not
  need the page). Tested both ways.
- **Coverage:** member-requested analyses take the same path and so are recorded too, within
  the budget. At 20-40 held stocks a weekday plus the Saturday dives, the 200 may be spent by
  Thursday or Friday; those entries read `budget`, and the read judges each engine on the
  decisions it was called for (card).
- **Low, to BACKLOG B-20:** the shadow's OpenRouter cost is in its rows, not in the LLM call
  log; `search_shadow.jsonl` has no rotation (about 6 MB a week at both engines' full budget,
  from Parallel's longer excerpts); the address guard resolves before it requests, so DNS
  rebinding is not caught.
- **Fixed in the phase:** the hook's warning lacked `exc_info`, which the analysis hot path
  requires (the guard test above).
- No medium or higher finding.
