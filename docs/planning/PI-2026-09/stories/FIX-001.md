# FIX-001 — Use a one-bar price download instead of discarding it

Priority: **P1** · Scope: **user-requested** (owner, 1 Oct 2026, about 00:36 IST) · Estimate:
**1 point**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: none. Source: the
diagnosis of the 30 Sep ops alert "audit_nightly completed 25/27", recorded as a note on the
[SA-040](SA-040.md) card.

## Intended result

On a stock's listing day, a price download holds exactly one bar. The close fetcher discarded a
one-bar frame: `df["Close"].squeeze()` turned it into a scalar, and `.dropna()` raised. So the
session's own close was lost, and only the NSE cross-check was left.

**Example.** On 30 Sep the nightly audit graded the IPO lane's listing-day rows:
- ELEVATE and ARMEE: the NSE fallback supplied the close, and they were graded;
- SWASTIKAIN and ADROITIND: no source answered, so both were `skipped_unpriceable`.

The listing-day row is the only IPO row that can carry a right/wrong mark. After this fix the
one bar is read like any other, so those rows get their close from the download.

## Acceptance criteria

- A one-bar download for the requested session gives that close, dated that session, in
  `daily_review._fetch_session_close`. That covers the review, the audit and
  `core.portfolio.pricing.close_on`.
- A lone bar from an earlier session is carried forward visibly: it is dated its own session, not
  the requested one. This is the same rule as for a longer frame.
- A lone NaN bar is still no close.
- The BSE fallback reads a one-bar frame.
- `close_verifier._fetch_yfinance_close` reads a one-bar history. A NaN last row is still a
  failure, not the previous day's close.
- Frames with two or more bars behave exactly as before.
- Tests use expected values written by hand from the fixture bars. The original defect makes
  them fail.
- The KT (sections 4 and 8) and guide case 05-G describe the behaviour.

## Starting points

- `core/intelligence/rl/workflows/daily_review.py`: `_fetch_session_close._extract`
- `services/data/fetchers/close_verifier.py`: `_fetch_yfinance_close`
- `core/audit/outcomes.py` (`grade_ipo_lane`, `_default_price_fn`) and `core/portfolio/pricing.py`
  (`close_on`): consumers only
- `tests/unit/test_session_close_sa003.py`, whose comment named this case as pre-existing

## Not in scope

The indicator fetcher's `squeeze()` calls (`core/intelligence/algorithms/indicators/fetcher.py`)
work on year-long histories. A one-bar history gives no indicators either way.

## Hard review

Trace the listing-day row from `grade_ipo_lane` through `close_on` to the stored outcome. Check
that no stale close is ever passed off as the session's own. Check that the multi-bar selection
is byte-for-byte the same behaviour.

## Rollout

After the fresh review, commit and push in a job-free window. No configuration changes.
Production check: the next nightly audit with a listing-day IPO row shows no
`skipped_unpriceable` for it, and no `'numpy.float64' object has no attribute 'dropna'` line.
