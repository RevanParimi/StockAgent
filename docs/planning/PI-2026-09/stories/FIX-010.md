## Intended result

Each analysis is recorded in the score history, so the screens that read it show real, dated
analysis states. A screen that lists stocks names only stocks the viewer may see.

**Example.** The member holds WELCORP. The 16:30 analysis turns WELCORP from BUY to SELL. The
owner alone asked the chat about STARHEALTH.

- **Today (production):**
  - Home's watchlist says "Not analysed" for every stock (after PR-001's deploy; before it, a
    made-up 0.50 NEUTRAL).
  - Portfolio's "Recent verdict changes" lists nothing. If forecast misses exist, it says "No
    verdict changes in the analysed stocks".
  - The chat's "CURRENT VERDICTS" context is empty. Its analysis tool finds no saved run, so each
    question about a stock starts a fresh analysis, which can take up to 45 seconds.
- **After the fix:**
  - Home shows WELCORP's score and verdict (dating the watchlist score stays with SA-024).
  - Portfolio lists "WELCORP: BUY → SELL" on the day it happened.
  - The member never sees STARHEALTH, which is in the store only because the owner asked about
    it.

## Acceptance

1. **The write.** Every completed analysis saves one score-history row, from the single exit that
   already logs `run_summaries`: once the decision gate has run, with the verdict the analysis
   returns.
   - This covers every entry point: the 16:30 review, the monthly forecast, discovery deep dives,
     `/analyse`, the stream route and the chat's `run_agent_analysis`.
   - A failed write logs a warning and never fails the analysis. Catch the store's real errors
     (`sqlite3.Error`, `OSError`), not `Exception`; the broad-except guard stays green.
   - A failed analysis writes nothing.
   - Retention stays `SCORE_HISTORY_MAX_ROWS` per stock (the store prunes on save).
2. **Who sees which stocks.** Readers that list stocks out of the store show only:
   - the viewer's own holdings and watchlist;
   - the managed tickers;
   - the active shelf ideas.

   They never name a stock that is there only because another account holds it, watches it or
   asked about it (FIX-009's rule). These readers are:
   - `/ui/learnings` (today it walks the 16 automobile stocks instead);
   - the chat's `_ctx_current_verdicts` and `_ctx_recent_history`.

   Readers keyed by a stock the viewer names are fine: the watchlist row for the viewer's own
   symbol, `_ctx_ticker_detail`, the chat's cached analysis, search and `/history/{ticker}`.
   - `/ui/learnings` takes the session user, as `/ui/watchlist` does. With AUTH off it is the
     default user.
   - Inspect every caller before editing (`grep _score_store`, `get_all_latest`,
     `get_by_date_range`).
3. **Watchlist rows.** A watched symbol outside the 16 automobile stocks shows its score history
   too. Today `get_watchlist` returns `hasData: false` for it without looking (`ui_data.py`,
   `_fetch_one`). Its price may stay "—": a price lookup for such symbols is out of scope.
4. **The empty case.** With no recorded change, Portfolio does not state a bare absence. It says
   since when it has been looking, for example "No verdict changes since 16 Oct" (the oldest kept
   run among the listed stocks). The exact wording is the implementer's call, recorded in the
   receipt.
5. **Optional backfill, run only at the owner's explicit word at rollout.** A script copies
   `run_summaries` rows into `score_history`. It is a production data write.
   - Fields: ticker, `ts` as `run_at`, `final_score`, verdict, company; thesis empty.
   - Each row is marked as backfilled, so it can be removed.
   - Idempotent: a second run adds nothing.
   - It never adds a row at or after a stock's first live row.
   - It keeps at most `SCORE_HISTORY_MAX_ROWS` per stock.
   - It prints dry-run counts first, and needs a backup first (the existing backup tooling).

   **Example:** with the backfill, Portfolio shows the newest of the last 30 days' changes the
   morning after the deploy, and Home shows scores at once. Without it, Home fills after the next
   16:30 review, and a change appears only after a stock's next differing analysis.
6. **Tests.** Independent of the changed code: deterministic fakes for the agents and the LLM,
   real `ScoreStore` and telemetry files in a temp folder, and no network. They must cover:
   - one analysis through the real orchestrator exit writes exactly one row, with the gated
     verdict, and a second analysis adds a second row;
   - a store failure leaves the analysis result and its `run_summaries` row intact and logs a
     warning;
   - a guard that no analysis entry point bypasses that exit (or one test per entry point);
   - the privacy case:
     - the owner holds AAA, the member holds BBB, the member asked the chat about CCC, the
       managed list has MMM and the shelf has SSS, and each changed verdict;
     - the member's `/ui/learnings` and chat context show BBB, MMM and SSS, never AAA;
     - the owner's show AAA, MMM and SSS, never BBB or CCC (the store does not record who asked,
       so CCC is not on the member's list either; the member can still ask about it by name);
   - a watched non-automobile symbol with a score row shows its score;
   - the empty case's wording;
   - the backfill: dry-run counts, idempotence, the live-row cut-off, the cap, the marker, and
     that nothing outside the temp folder is written.
7. **Documentation, as current design.**

     may name. Add KT section 12's FIX-010 row (`Open` until the commit) and rebuild the PDF.
