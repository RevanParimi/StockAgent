# FIX-021 — A Google redirect link is not an article's identity

Priority: **P2** · Scope: **found in production** on 2026-10-31 from Serper's notice of a change
on 30 Oct (the owner pasted the email; session `stockagent-main-6b`) · Estimate: **1 point**

Status lives in [STATE.json](../STATE.json), not this card. No dependency. **Order:** directly
before [SA-048](SA-048.md), so it is the next story (routing delegated by the owner on
2026-10-13). The reason: until it ships, every event-feed run can store news rows under a
redirect link, and those rows stay (this card changes no production data). **Revisit trigger:**
move it back after SA-048 if the owner wants SA-048 first; nothing depends on it.

## What changed at Serper

Serper's email to the owner (30 Oct 2026): "Since about 01:30 UTC on October 30, Google only lets
a few result links be opened right after a search. Because of this, links after the top 3
results now come back as google.com/goto links instead of the real URLs." The top 3 are resolved
automatically (under half a second more per search). Serper's free `/resolve` endpoint returns
the real URLs for the others, taking about 30 seconds after a search. Serper's instruction page
(`serper.dev/google-links`) renders in a browser only, so its request format was not read.

## What was found

**Measured (production, read-only).** The owner ran
`analysis_data/serper_goto_2026-10-31/events_link_probe.py` (ignored) on 31 Oct at 08:22 IST.
It prints counts only: per fetch day, the news events stored, those whose `source_url` is on
google.com, and repeats (same stock and title already stored under another id).

| Fetch day | News events | google.com links | Repeats |
|---|---:|---:|---:|
| 26 Oct | 15 | 0 | 0 |
| 27 Oct | 14 | 0 | 1 |
| 28 Oct | 23 | 0 | 0 |
| 29 Oct | 23 | 0 | 0 |
| 30 Oct | 31 | **5** | 0 |

So `/news` is affected, not only `/search`, from the first run after the change (07:00 IST on
30 Oct). No repeat has landed yet. The 27 Oct repeat predates the change.

**From the code (inspection):**

- **Company-event feed (live).** A news item's identity is its link: `news:{digest(url)}` in
  `core/events/sources.py` (`news_items`). Nothing else ties two rows to one article: the store
  skips a known id and the classifier's `duplicate` is within one call. Example: on the morning
  run "Maruti wins export order" is result 2 with its real link and is stored. On the evening
  run (both search the past 24 hours) it is result 4 under a `google.com/goto` link. The feed
  takes it for a new article, pays a classifier call and stores a second event. The daily
  review's dossier and the evidence exit's watch list then show it twice. A news event cannot
  sell: `CASE_EVENT_SOURCES` in `core/portfolio/advisor.py` holds NSE sources only.
- **IPO grey-market price (switched off: `ipo.gmp_enabled: false`).** `_numbers_by_domain` in
  `services/data/fetchers/ipo_gmp.py` needs two different sites. Results 4–6 would all be the
  one site "www.google.com", so a redirect could stand in for a real source.
- **Chat news search (live).** `_rrf_fuse` in `services/api/routes/ui_data.py` merges results by
  link, so one article can be listed twice, and the model is shown the redirect link.
- **Macro headlines (live).** `services/background/macro_news_fetcher.py` makes its own `/news`
  call and keeps the link as the headline's `url`.
- Analyst news context, macro and sector searches read title, snippet and date only.

## Intended result

- **At the fetch boundary, a Google redirect is no link.** Where a Serper response is parsed
  (`search_serper` and `search_serper_news_status` in `services/data/fetchers/news.py`, and the
  macro headline fetcher), a link on google.com, or any subdomain of it, is replaced by "". The
  callers already treat "" as no link:
  - the event feed drops the article (`news_items` drops a row without a URL);
  - the IPO check does not count it (`_numbers_by_domain` skips an empty domain);
  - chat fuses by title (`_rrf_fuse` falls back to the title).
  Check each caller, the macro headline's display included; do not assume it.
- **Counted, not silent.** The event run record counts the articles dropped this way
  (`news_redirect_links`), so the owner can see how many each run loses.
- **No Serper `/resolve` now.** It adds about 30 seconds and a second request path, and its
  format was not read. Revisit it if the run record shows that redirects make up more than a
  quarter of the feed's articles over five trading days.
- **No production data change.** Rows already stored under a redirect link stay: 5 from 30 Oct,
  plus any from runs before the deploy. The receipt states this. Removing them would be a
  production data change, which needs the owner's word.
- Add no registry, framework or new Serper call.

## Acceptance criteria

- **Idempotency invariant (hermetic, independent of the implementation):** one article fetched
  in two runs, once at rank 2 with its real URL and once at rank 4 with a `google.com/goto` link,
  yields exactly one stored event and one classifier item, in either order.
- Parser tests for `/search` and `/news`: a google.com link (www and bare host) becomes "", and a
  publisher link, including one whose path or query contains "google", is unchanged.
- The IPO check: a google.com result never counts as a source. One real site plus redirects is
  fewer than `ipo.gmp_min_sources`.
- Chat: one article, with its real link in one variant and a redirect in another, appears once.
- The macro headline never shows a redirect as its link.
- The run record's `news_redirect_links` counts the dropped articles.
- KT section 4's event-feed step 5 and section 12's row describe the rule; regenerate the PDF.
  Update guide case for the event feed if it describes an article's identity.
- The story file, the changed files and the full suite pass.
- **Production verification (separate, after the deploy):** re-run the probe. No news event
  fetched after the deploy carries a google.com link, and the run log shows
  `news_redirect_links`.

## Hard-review questions

- Is the redirect test exact? A publisher URL that merely contains "google" must keep its link.
  A google.com link must lose it on every Serper path, macro headlines included.
- Does any caller turn "" into something worse: a crash, an "about:blank" link, a key shared by
  every article without a link?
- Is the invariant test independent of the code's own helper, for example by building the two
  Serper responses by hand?
- Are the rows already stored under redirect links stated in the receipt, with no attempt to
  rewrite production data?
