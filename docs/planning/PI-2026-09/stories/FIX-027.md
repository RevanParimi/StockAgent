# FIX-027 — A decision booked at a session's close reads nothing from after that close

## What was found

**M1, medium (issue time, pre-existing since the Living Envelope; found answering FIX-024's
hard-review question): an ADD or a sale booked at a session's close can rest on what happened after
that close.**

The 16:30 job on day T reviews the previous session D, then runs the portfolio pipeline, which
books its trades at D's close
([scheduler.py](../../../../services/scheduler/python/scheduler.py) lines 771 and 962). FIX-023 and
FIX-024 closed this for the regime and for new positions. The advisor's **envelope** is still open:

- **The review's own re-forecast.** On an external shock, a thesis break or a flip into crisis, the
  review of D calls `regenerate_envelope`
  ([daily_review.py](../../../../core/intelligence/rl/workflows/daily_review.py) line 1532), on day
  T. It runs a live analysis with no as-of date, and anchors the new path on
  `_fetch_actual_close`
  ([generate_forecast.py](../../../../core/intelligence/rl/workflows/generate_forecast.py) line
  90), which reads "the most recent close": T's, not D's.
- **The pre-open check.** At 08:45 on day T, `preopen_check.py` re-forecasts on overnight news. That
  afternoon's run reviews D and reads the result.
- **The advisor** reads whatever envelope is there. `build_signals` measures the drift against D's
  close ([advisor.py](../../../../core/portfolio/advisor.py) line 220).
- **The event does not say when.** `ReforecastEvent.date` holds D, and no time is stored, so
  nothing downstream can tell.

**By example.** Monday's close is ₹1,000; Tuesday's is ₹1,100, on results.

- Tuesday's 16:30 run reviews Monday. Its re-forecast starts from ₹1,100. The advisor compares that
  path with Monday's ₹1,000, reads +10%, "UP", and ADDs at ₹1,000, dated Monday. The record gains
  ₹100 a share on the tranche the moment it buys, on a price the run knew had gone.
- With Tuesday at ₹900 and the review saying "thesis not intact": the path reads DOWN, and the
  price-path rule EXITs at ₹1,000, dated Monday: sold before a fall the run had already read. The
  example in KT section 6 ("the re-forecast path ends at ₹470") is this flow.

**Where it reaches.**

- ADD (25% of the holding), the `thesis_break` EXIT and the SWITCH built on it, all live.
- `shock_reforecast` too, once [FIX-015](FIX-015.md) makes it fire.
- **The exit-rule switch gate (inference):** a row is graded from the decision's close, so a legacy
  sale on day T's fall counts that fall in the legacy rule's favour. The shadow has been writing
  rows since 30 Oct.
- Not deployment or a new position's buy: FIX-023 and FIX-024 cover those. A SWITCH's sell leg is
  reached; its buy leg is not.

**Bounded.** At most 2 re-forecasts per ticker per month (`rl.reforecast_max_per_month`), and an ADD
also needs position headroom and 60% accuracy. Each one moves the record by at most one session's
move on the shares traded.

## Intended result

1. **Measure first.** A counts-only read-only probe (the owner runs it; no logs, no user ids):
   re-forecast events per month since 1 Aug, by trigger, and how many have an ADD, EXIT or SWITCH
   advice on the same holding on that review date. Record the numbers in the receipt.
2. **Say when.** `ReforecastEvent.at`: the time it ran, in IST. The review's re-forecast anchors on
   the review session's close, not the most recent one.
3. **A decision reads the envelope as it stood at the close it is booked at.** A re-forecast made
   after D's close (`close_before_decision`, the one rule) cannot set `envelope_direction` for a
   decision at D's close. Which path it reads instead (the archived envelope is there:
   `ReforecastEvent.archived_file`) is the implementer's call, recorded.
4. **An ADD** that only the later path would allow does not fire. Reason on the record, as for
   `REGIME_UNAVAILABLE`.
5. **A sale: the owner decides**, from the example above, before implementation. Two options:
   - **Wait (recommended if the count is small).** Tuesday's run does not sell at ₹1,000. The
     re-forecast ran at Tuesday 16:45, after Tuesday's close too, so it first counts for Wednesday's
     close, booked by Thursday's run. Honest, and two sessions late.
   - **Book it at the latest close the run read.** Tuesday's run sells at ₹900, dated Tuesday. No
     delay, and the price is the one the decision saw, but one run then books trades at two
     sessions' closes, which touches the ledger's dates, the idempotency reference and the marks.
   A larger option, for the owner to know about, not this card: run the job after the session's data
   is final and review that same session, which removes the one-session gap everywhere.

## Acceptance

- RV13's shapes, as tracked tests with hand-worked figures: Tuesday ₹1,100, no ADD at Monday's
  ₹1,000; Tuesday ₹900, no EXIT at ₹1,000 (or the owner's option). A re-forecast dated before the
  decision's close still counts: an envelope re-forecast last week ADDs as today.
- An independent invariant over re-forecast times and review sessions: the direction a decision at D
  reads never depends on a close or a run after D's close. The pre-open path included.
- Old envelopes parse (no `at`): their events are from before the decision.
- The KT section 6 limit added by FIX-024's commit is removed; section 12's row; a guide case.
