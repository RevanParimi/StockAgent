# PR-033 — Read every deployed story's production watch once, and write the one list

Priority: **P1** · Scope: **owner request** of 2026-11-16 ("I am worried about this") · Estimate:
**3 points** · Lane: **light** (it reads production and records; no code path changes)

Status lives in [STATE.json](../STATE.json), not this card. No dependency. **Order:** right after
[FIX-032](FIX-032.md); [PR-034](PR-034.md) builds on its list. Profit-path step: **measure**.

## Why

On 16 Nov 2026, 38 accepted stories are "deployed, still being watched"
(`production_verification.status` = `pending_observation`). Their code runs in production, and
nobody has read real runs to confirm it does what it should.

- Each watch is a free-text "Next: look at…" note inside the story's STATE entry.
- None has a due date. Nothing triggers the look.
- Production cannot read STATE.json, so the watchdog knows none of them. Its registry
  (`config/milestones.yaml`) holds 1 dated milestone and 12 standing checks.
- Only watches that were also written into STATE `pending_production_checks` (PR-014's three, for
  example) are picked up, and only when a conversation happens to start.

**Example.** FIX-021 (a Google redirect link is not an article's identity) went live on 31 Oct. Its
note says to re-run a probe. No date says when, so on 16 Nov it is still unread. If the fix did not
hold, the event feed has been repeating articles for two weeks and nothing said so.

Six more labels look stale: SA-011, FIX-007, FIX-008, FIX-009 and PR-001 say `pending_deployment`
and CLEAN-001 says `not_deployed`, yet their commits are in `1913017`, which production runs.

## What to do

1. **State each watch in one shape.** For every `done` story whose production status is not
   `verified` or `not_applicable` when this card starts (44 on 16 Nov), write:
   - **occasion:** a time the feature had a chance to act, countable in production data;
   - **violation:** a time it acted wrongly;
   - **since:** the deploy date;
   - **needed:** how many occasions make a fair look (default 5; 1 for a weekly or monthly job).

   Examples: FIX-021: occasion = a news event stored after 31 Oct, violation = one whose link is a
   Google redirect. SA-048: occasion = a paper trade after 1 Nov, violation = one with no cost
   line. FIX-030: occasion = a Saturday deep dive on the general path, violation = one filed under
   a sector its own analysis did not name.
2. **One read-only probe**, `analysis_data/pr033/watch_probe.py` (ignored folder): counts and
   symbols only, no user ids, emails, raw logs or environment. Group the watches by the file they
   read so each file is opened once. Dry-run it locally, then run it once through `railway ssh` at
   the owner's word in that conversation.
3. **Give every story one outcome**, with its counts and the date:
   - **verified:** enough occasions, no violation. STATE says `verified`.
   - **failed:** any violation. A fix card if it is on the decision path and medium or higher,
     else a [BACKLOG.md](../BACKLOG.md) entry (AGENTS.md rule), each with a money example.
   - **waiting:** too few occasions. A dated row (below).
   - **needs eyes:** only a person can judge it (a screen reads right). A dated row naming its case
     in `docs/TEAM_TESTING_GUIDE.md`.
   - **closed:** production cannot show it, or the feature is gone. The owner confirms the list of
     closures; each records why its tests stand in.
4. **The one list.** Every waiting and needs-eyes watch becomes a row in STATE
   `pending_production_checks` (the shape already there: `id`, `story`, `due_ist`, `status`,
   `check`, `trigger`, `record_in`), with a deadline: 8 weeks after the deploy, or the next natural
   event (a month start, a results season) if that is later. The free-text "Next:" notes then point
   to the row.
5. **Correct the six stale labels** from what `git merge-base --is-ancestor <commit> origin/main`
   and the deploy record show; note any that still needs a setting turned on.

If 44 stories do not fit one conversation, split by deploy month (September and October; November)
and record the split in STATE before starting the second half.

## Acceptance criteria

- No `done` story is left `pending_observation`, `pending_deployment` or `not_deployed` without
  either a verified record or a dated row in `pending_production_checks`.
- The receipt lists every story: its shape, counts, outcome and where a failure was routed.
- The probe output holds counts and symbols only; the raw output stays in `analysis_data/`.
- Nothing in production changed: no deploy, variable, job trigger or data write.
- `check_kt_docs` stays clean (STATE is read by it).
