# SA-002 — Make data-health records describe usable evidence

Priority: **P1** · Sprint: **1** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: none. Evidence: F07 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

A returned string is not proof of usable source data. Distinguish verified data, empty response, stale data, failure and a synthetic fallback.

Introduce a small typed fetch-result contract with source, as-of time and reason. Preserve existing blank/exact-unavailable handling. Derive health from essential sections and live dimensions; version the telemetry contract.

## Starting points

- `services/data/context/bundle_builder.py`
- `services/data/stores/data_health.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- Provider no-data messages never become healthy merely because they are nonempty.
- A 9-dimension result with only one live source cannot report fully healthy.
- Existing telemetry readers accept legacy rows and explicitly label unknown provenance.

## Unit and integration evidence

- Parameterize empty, exception, provider error text, stale cache, synthetic and verified result cases.
- Integration fixture checks bundle -> health row -> watchdog/UI meaning; no provider calls.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Hard review

Check every producer supplying an essential price/fundamental section; a string-guessing patch alone fails review.

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Deploy telemetry changes additively; old rows stay intact. Compare health rows to correlated source logs across one complete scheduled cohort.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.

## Handoff

At implementation completion, write `evidence/SA-002-implementation.md`, capture the changed-file manifest and diff digest, set status to `review_required`, and update HANDOFF.md. At accepted review write `evidence/SA-002-review.md`, mark code completion, and leave any deployment or future-cohort verification pending explicitly. Execute one phase per conversation.
