## Routed input — 2026-09-22 DOC-001 review (F5)

Two tests in `tests/unit/test_atlas_outbox.py` depend on an ambient
`DELIVERY_EMAIL_TO`: `test_send_row_caps_push_and_passes_html_to_email` and
`test_send_row_returns_transport_reason`. `outbox._send_row` calls
`resolve_recipient()`, which returns `""` with no `users.db` row and no
`DELIVERY_EMAIL_TO`. The row then fails with `no email on file for user 'u1'`
before the monkeypatched `send_email_result` is reached. The tests pass in a
normal developer run only because dotenv loads the real address from `.env`.

Reproduced locally 2026-09-23 (Windows, Python 3.13.11):

```text
DELIVERY_EMAIL_TO="test@example.invalid" pytest tests/unit/test_atlas_outbox.py -q  -> 11 passed
DELIVERY_EMAIL_TO=""                     pytest tests/unit/test_atlas_outbox.py -q  -> 2 failed, 9 passed
```

This falls under the first acceptance criterion (full suite runs without
`.env`). The fix belongs in the tests, by patching the recipient resolution or
seeding a fixture account. Do not weaken `resolve_recipient()`, and do not make
the assertions depend on any real address.

## Routed input — 2026-09-26 SA-001 review (L1)

SA-001's security regression test runs in a real browser, so it only runs where Node, `npm ci` and Playwright's Chromium exist. Without them, `tests/unit/test_chat_markdown_boundary.py::test_chat_markdown_browser_suite` **skips** with a reason, and the Python suite still passes. The repository has no CI workflow (`.github/workflows` is absent), so today nothing guarantees the suite runs before a push. The baseline this story establishes should run `npm ci`, `npx playwright install chromium` and `npm run test:frontend` (about 25 s), or make that skip a failure in CI. Do not drop the browser run in favour of the static guards: the static guards cannot see an executing handler. See the [SA-001 review](../evidence/SA-001-review.md).

## Routed input — 2026-09-26 SA-002 implementation (T2)

The suite has no network guard, and a mock on the wrong name fails open. During SA-002, `tests/unit/test_bundle_builder_sectors.py` still patched `fetch_news_context`, `fetch_tavily_context`, `get_valuation_context` and `get_raw_materials_context`, while the producers had moved to their `*_result` siblings. One intermediate run of that file therefore reached the real providers with the developer's `.env` keys. The local usage counters moved +2 Serper and +10 Tavily; public yfinance calls were also made, and 8 Tavily month-cache pairs were written under `data/tavily_cache/` (then deleted). The patches were retargeted, and the SA-002 tests carry their own autouse guard. A suite-wide autouse guard in `tests/conftest.py` would make any future miss fail loudly instead. It should fail every non-loopback `socket.connect` and `getaddrinfo`, and allow loopback, because asyncio on Windows uses a 127.0.0.1 socketpair. That is also the check T1 above asks for.

**Measured with that guard, 2026-09-26.** The existing suite is not network-free. A full `tests/unit` run (3300 passed) attempted **194** outbound connections, all blocked:

| Host | Attempts | Test files |
|---|---|---|
| `openrouter.ai` | 120 | `test_absurd_price_error.py` 48, `test_shock_path.py` 36, `test_hard_bind_daily_review.py` 24, `test_daily_review_dossier.py` 12 |
| `www.nseindia.com` | 68 | the T1 harness, across 9 RL files |
| `google.serper.dev` | 6 | `TestSalesDemandAgent::test_run_calls_llm` in `test_agents_unit.py` and `sectors/automobile/test_agents.py` |

All of these predate SA-002: the same files on the pre-SA-002 code make the same attempts, and the Serper ones appear whenever a key is set. **In a normal developer run with `.env` keys, these are real calls, and the OpenRouter ones likely spend LLM credit on every suite run.** The guard is in ignored `analysis_data/sa002/nonet.py`, and the attribution is in [the SA-002 receipt](../evidence/SA-002-implementation.md).

## Routed input — 2026-09-27 SA-003 implementation (test isolation)

- **The config loader stays reloaded.** `tests/unit/shared/test_config_loader.py` reloads
  `backend.shared.config.settings.loader` against a throwaway YAML and never reloads it back, so
  every later `cfg()` read in the same run sees that file. Example: SA-003's check that
  `config.yaml` ships `decision_gate.mode: record` read `None` in the full run and passed alone. It
  now reads the file itself. Any later test that reads a shipped default through `cfg()` passes or
  fails by collection order.
- **Two portfolio-pipeline tests depend on the developer's `data/atlas.db`.** With
  `atlas.enabled: true` and 0 users in the local database, `active_user_ids()` returns `primary`.
  `test_portfolio_pipeline.py::test_pipeline_end_to_end` and
  `::test_pipeline_holding_failure_is_non_fatal` then fan out to the wrong user. They fail when run
  alone, identically on unmodified `da90ee5`, and pass in the full run (by order) or with
  `ATLAS_ENABLED=false`. These tests, like `add_holding` generally, also write
  `upsert_user_instrument` rows to the real local `data/atlas.db` (the FK errors in their logs).
- **The known locking flake, measured again.**
  `test_portfolio_locking.py::test_cross_process_add_holding_is_atomic` failed once in a full run
  and 1 of 3 times alone in the OneDrive checkout: lost updates, `SYM18` and `SYM19` at quantity 1.
  It then passed 10 of 10. In a temporary worktree it passed 12 of 12: 6 on baseline code and 6
  with SA-003 applied. SA-003 does not touch the store.
