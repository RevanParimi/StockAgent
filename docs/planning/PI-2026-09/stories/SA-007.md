# SA-007 — Make backups independently recoverable

Priority: **P1** · Sprint: **1** (moved from 2 on 2026-09-23) · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: none. Evidence: F17 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Local backups exist, but the off-site email path repeatedly fails. Recovery must not depend on the same application volume or delivery channel.

Document retention and a minimal independent object-storage backup adapter with integrity metadata. Prepare configuration without provisioning paid resources automatically. Restore into an isolated directory and validate representative stores.

## Starting points

- `services/data/backup.py`
- `core/ops/watchdog`
- `tests/unit/test_backup.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- Backup artifacts include consistent SQLite snapshots and required JSON/JSONL state.
- A restore drill validates schema, row counts, ledger continuity and checksums.
- Missing off-site confirmation is visible; secrets are excluded from artifacts/logs.

## Unit and integration evidence

- Test interrupted upload, corrupt archive, missing manifest, retention boundary and failed restore.
- Use a temporary filesystem/SQLite DB for recovery; never restore over production.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.
