# SA-011 — Turn durable errors into a deterministic operations backlog

Priority: **P2** · Sprint: **2** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-002](SA-002.md), [SA-004](SA-004.md). Evidence: F21 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Durable logs exist, but repeated warnings and failed delivery are not grouped into a useful issue lifecycle.

Add stable fingerprints, first/last seen, count, affected run IDs and new/regressed/spiking states. Surface an authenticated digest/registry through the watchdog with bounded retention.

## Starting points

- `core/ops/watchdog`
- `core/delivery/ops_alerts.py`
- `services/api`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- INFO text on Railway stderr is not classified as an app error solely from its outer envelope.
- Identical causes group without leaking user payloads or secrets.
- Acknowledged issues can regress; pending verification milestones reconcile against measured evidence.

## Unit and integration evidence

- Test changing timestamps/IDs, traceback variants, repeated warning floods, severity parsing and tenant authorization.
- Verify deterministic digest output and retention without losing active issues.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.
