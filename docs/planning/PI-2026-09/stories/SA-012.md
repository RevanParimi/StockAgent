## Routed input — 2026-09-27 SA-003 review (F2)

The realized close is part of this target, and the close verifier can pick the wrong session's
close. See [the SA-003 review](../evidence/SA-003-review.md), finding F2. This predates SA-003.

- **Example.** A review for Fri 25 Sep. yfinance has Friday's bar, with a close of 110. NSE's
  history does not list Friday yet, and its newest row is Thu 24 Sep, with a close of 100.
  - `_fetch_nse_session` takes that Thursday row: `row = match or data[-1]`, at
    `close_verifier.py:126-129`.
  - The two closes differ by more than 1%, so `_compare` prefers NSE's (`:157-168`).
  - The "verified" close for Friday is therefore 100, from Thursday.
  - Before SA-003 that day was graded against Thursday's close. Since SA-003 the close is dated
    Thursday, so it is not fresh. `record` logs it; `enforce` skips the review. The skipped days
    are then mostly big-move days.
- **Fix direction.** When a session is requested and NSE has no row for it, treat NSE as
  unavailable for that session; do not take an earlier row. Then yfinance's session close stands,
  with source `yfinance`. Add the lag case as a table test: yfinance has the session, NSE lags,
  and the difference is above 1%.
- **Measure first.** SA-003's `record` mode counts it. Look for `decision_gate.jsonl` rows with
  `stage: actual_close` whose reason names `source nse` and the previous session's bar. How often
  NSE lags at 16:30 IST is not yet measured.

## Routed input — 2026-09-27 SA-005 implementation (date-pinned test runs)
