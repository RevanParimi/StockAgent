# SA-015 — Make adaptive updates idempotent and preserve final weight bounds

Priority: **P1** · Sprint: **3** · Provisional estimate: **5 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-014](SA-014.md). Evidence: F10, F11 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Retries can advance weights repeatedly while replacing one feedback row. Normalization can violate the bounds applied immediately before it.

Use an explicit as-of clock and outcome/update ID; atomically persist feedback, applied-update checkpoint and new weights. Enforce constraints on the final simplex vector; reject infeasible configurations explicitly.

- `core/intelligence/rl/workflows/daily_review.py`
- `core/intelligence/rl/stores/prediction_store.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- The same matured outcome changes weights at most once, including concurrent attempts and crash recovery.
- Backfills never consume future rows or use today's date implicitly.
- Final weights sum to one and satisfy nonnegativity, absolute drift and per-step constraints.

## Unit and integration evidence

- Regression: ten 0.1 weights, nine -0.05 and one +0.05 deltas must not yield 0.25 under a 0.15 upper bound.
- Property tests cover feasible/infeasible constraints and deterministic ordering.
- Fault injection covers crash between writes, retry and competing processes.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Routed input — 2026-09-27 SA-004 implementation (a scheduled rerun)

The scheduled job reruns a session at every weekday NSE holiday, with no crash or operator
involved. `rl_daily_review` runs Mon–Fri at 16:30 (`FEEDBACK_CRON "30 16 * * mon-fri"`), and
`_daily_review_job` does not skip a non-trading day. Checked against `nse_calendar`:

- Fri 2 Oct 2026 is a holiday. That day's job reviews `trading_days_ago(2 Oct, 1)` = Thu 1 Oct.
- Mon 5 Oct's job reviews `trading_days_ago(5 Oct, 1)` = Thu 1 Oct again.

So each ticker runs a full `run_daily_review` for 1 Oct twice. That is F10's rerun, next week in
production. SA-004 counts both runs as one cohort: attempts add up, completion does not. It does
not stop the second run's learning writes. Candidate fixes include this story's review-identity
checkpoint, or skipping the scheduled review on a non-trading day. The Friday run is then lost,
and Monday reviews 1 Oct once. See [the SA-004 receipt](../evidence/SA-004-implementation.md).
