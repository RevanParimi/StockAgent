# SA-024 — Show verifiable learning evidence and honest unavailable states

Priority: **P2** · Sprint: **5** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-019](SA-019.md), [SA-020](SA-020.md), [SA-022](SA-022.md). Evidence: F16, F24 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Users see changing weights without a clear account of whether previous suggestions beat a baseline. API failure can also leave demo metrics visible.

Show cohort dates, issue/target horizon, outcome counts, exclusions, matched baseline, method version and experiment decision. Distinguish live, provisional, demo, error and insufficient-data states visibly.

## Starting points

- `src/frontend/prototypes/rl-monitor.jsx`
- `services/api/routes/ui_data.py`
- `core/delivery/weekly.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- A reader can navigate from weekly/fortnightly summary to a frozen suggestion and its outcome.
- Unavailable production metrics never silently fall back to example accuracy.
- Weight movement is described as a policy update, not proof of learning.

## Unit and integration evidence

- API and UI fixtures cover no data, incomplete cohort, demo mode, failed fetch, stale report and harmful adaptation.
- Verify aggregate totals reconcile with drill-down and public responses exclude private ledgers.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Routed input — 2026-09-23 (found while writing SA-039)

**Code inspection, not a production measurement.** The verdict-shadow field `learned_weights_used` is `bool(weights passed)` (`signal_aggregator.py` L205). The orchestrator always passes a dict: learned weights or the defaults (`base_orchestrator.py` L149). So the field reads true even for a ticker with no learning state. `learning_evidence.py` L414 reports its count as `learned_weight_rows`, which overstates how often learned weights were used. Record the actual weight source instead (learned, default or contained), and use it in the evidence report.
