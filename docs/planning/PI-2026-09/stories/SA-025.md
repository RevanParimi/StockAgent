# SA-025 — Count actual provider calls and fallback cost

Priority: **P2** · Sprint: **6** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-011](SA-011.md). Evidence: F21 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Planner/fetcher-level counts can miss retries and fallbacks. Measure at transport boundaries before retiring code on assumed cost.

Instrument actual LLM/search/market request attempts with run ID, provider, retry/fallback cause, latency and available token/cost metadata. Mark unknown costs explicitly and redact payloads.

## Starting points

- `src/backend/shared/data/stores/api_usage.py`
- `services/data`
- `src/backend/shared`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- Retry and fallback attempts reconcile with mock transport calls exactly.
- No API key, authorization header or private prompt enters metrics.
- A run's cost can be attributed without assuming documented multipliers.

## Unit and integration evidence

- Test cache hit, retry, timeout, provider fallback, cancellation and nested callers without duplicate accounting.
- Verify durable writes do not break successful requests if telemetry storage degrades.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Hard review

Trace the provider boundary and compare counts to an independent stub request log.

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Keep instrumentation additive and bounded. Gather representative real fallback observations without deliberately causing expensive production failures.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
