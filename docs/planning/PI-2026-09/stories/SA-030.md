# SA-030 — Reconcile or retire stale Atlas projections

Priority: **P2** · Sprint: **stretch** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-009](SA-009.md), [SA-013](SA-013.md). Evidence: F19 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

JSONL advice is fresh while Atlas user_advice is an old ETL snapshot and ticker_verdicts is empty. Make projection authority explicit.

Inventory consumers and choose needed projections. Implement idempotent replay/checkpoints for those retained; deprecate unused reads/contracts. Keep original immutable ledgers authoritative.

## Starting points

- `core/portfolio/store.py`
- `services/data`
- `services/api/routes/ui_data.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- A retained projection reconciles counts/IDs against its source without duplicating rows.
- Crash/retry and late-arriving records converge; private tenants stay isolated.
- Empty/stale projections are visibly unavailable instead of silently treated as no advice.

## Unit and integration evidence

- Fixture replays duplicate, reordered, partially committed and conflicting records.
- Compare representative source/projection queries with tenant authorization checks.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Hard review

Review source-of-truth choice and all readers before migration. An empty SQL table alone is not evidence the live money loop stopped.

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
