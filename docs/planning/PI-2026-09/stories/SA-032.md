# SA-032 — Define and enforce the public-read and demo-data policy

Priority: **P2** · Sprint: **stretch** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: [SA-001](SA-001.md), [SA-024](SA-024.md). Evidence: F24 in the [September audit](../../../audit/2026-09-10-repository-production-review.md).

## Intended result

Some intelligence endpoints intentionally permit anonymous reads. Specify which data is public and ensure demo states cannot masquerade as production.

Create an endpoint/data classification table, default private-ledger reads to authentication and test owner/member/anonymous boundaries. Obtain a product decision only for genuinely ambiguous intended public data, using a concrete route inventory.

## Starting points

- `services/api/routes/ui_data.py`
- `src/frontend/prototypes`
- `tests/contract`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- No private portfolio/advice/user identifier crosses an anonymous or other-tenant boundary.
- Intentionally public intelligence fields are documented and minimized.
- Error/demo/live state behavior is consistent across analytics readers.

## Unit and integration evidence

- Contract matrix tests anonymous, owner, member and other tenant for classified routes.
- Inspect payloads and nested fields, not just HTTP status; test failed API initialization.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Hard review

Differentiate intentional public research from a proven leak. Verify both server response filtering and client behavior.

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
