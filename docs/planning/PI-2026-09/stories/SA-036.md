# SA-036 — Record durable outcomes for every critical job

Priority: **P1** · Sprint: **1** · Provisional estimate: **4 points** (3 → 4 on 2026-09-24, see "Widened" below)

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: none. Evidence: §2.3(3) in the [2026-09-23 production assurance review](../../../audit/2026-09-23-production-assurance-review.md). Added 2026-09-23 at the user's request.

## Intended result

Only `ipo_deep_dive` and `daily_review` call `record_job_outcome`. The brief, digests, autopilot, backup, watchdog and IPO refresh leave only logs, and those go with each deployment. "Did the 08:50 brief run?" has no durable answer.

Record an outcome for every scheduled job and expose them in the scheduler status.

## Starting points

- `services/scheduler/python/scheduler.py`
- `services/data/stores/job_outcomes.py`
- `services/api/routes/scheduler_api.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- Every scheduled job records started/finished time, status, counts and an error class.
- A job that raises still records `failed`; a failed outcome write never breaks the job.
- `GET /scheduler/status` shows every job's last outcome.
- An inventory test fails if any registered job id has no outcome wiring.

### Widened 2026-09-24 — production observability design (owner decision D5)

Per §5.1 of the [production observability design](../../../superpowers/specs/2026-09-24-production-observability-design.md), this story defines the one outcome contract the other observability stories build on:

- One `record_job_run()` writes a **history** row to `telemetry.db.job_runs`, which survives redeploys. The row holds:
  - `job_id`, `scheduled_for`, `started_at` and `finished_at`;
  - `status`: `ok`, `partial`, `failed` or `skipped_by_gate`;
  - small JSON `expected` and `produced` counts;
  - `error_type`;
  - the deploy id and commit, from Railway's environment (verify the variable names).

  It also keeps `scheduler_job_outcomes.json` as the last-run view that `/scheduler/status` reads.
- `partial` means the job completed but produced less than expected. Example: the 23 Sep 17:45 IPO refresh ran, but 0 of 5 bid ladders were fetched.
- The same wrapper exposes two hook points, which do nothing until those stories land: the SA-042 witness ping and SA-034's post-job evaluation.

## Unit and integration evidence

- `expected` against `produced`: a refresh fixture with 0 of 5 ladders records `partial`. A job disabled by its gate records `skipped_by_gate`, not `failed`.
- A test per job wrapper, including a crashing job.
- The 24-job inventory check proves coverage.
- The outcome file survives a simulated restart.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Routed input — 2026-09-27 SA-004 implementation

SA-004 changed the `daily_review` record in `scheduler_job_outcomes.json` (implemented, awaiting
its fresh review). Build the one contract on it, not beside it:

- **Its fields.** `status` is one of `ok`, `partial`, `failed` or `empty`. Every enabled ticker
  is disabled in `empty`. The record also has `required`, `attempted`, and the five outcome
  counts: `completed`, `degraded`, `data_gated`, `skipped` and `failed`. It carries `missing`,
  `by_ticker`, `retried`, `runs`, `excluded`, `duplicates` and `pipeline_status`. The legacy
  `produced`, `expected` and `pipeline_ok` are kept.
- **Map the vocabularies.** SA-036's list is `ok`, `partial`, `failed` and `skipped_by_gate`.
  Decide whether `empty` stays or maps to one of those, and say which.
- **Example: the pipeline's own count.** A user has 5 holdings, and every advisor call raises.
  `run_post_review_pipeline` catches each one, logs a warning and still returns
  `{"status": "completed", "advice": 0}`. SA-004 makes `pipeline_ok` false only for a malformed
  or raising pipeline, and when a review failed. It does not see failures inside the pipeline.
  Record the pipeline as `partial` when holdings failed.
- **Manual reruns are not recorded.** `POST /scheduler/daily-review` and the startup self-heal
  backfill run reviews without recording a job outcome. A manual rerun is therefore not merged
  into the day's record; only a second scheduled run of the same session is.

## Routed input — 2026-09-27 SA-004 review (F1, I1, I2)

- **F1 (low, reproduced): the outcome bookkeeping can stop the portfolio pipeline.**
  - **Where:** in `_daily_review_job`, the block that runs `ro.summarize`, `ro.missing_detail` and
    the summary log (`scheduler.py:893-897`) sits between the harvest and the tail, with no guard.
    It merges the previous `daily_review` record for the same session from
    `data/scheduler_job_outcomes.json`.
  - **Example:** suppose that record is valid JSON with a wrong type, such as `"attempts": [1]` or
    `"runs": "two"` (`review_outcomes.py:152`, `:171`). On the next same-session run (Mon 5 Oct
    after Fri 2 Oct), `summarize` raises. The job then crashes before the alerts, the portfolio
    pipeline and the outcome write:
    - `alert_job_crashed` pages;
    - the day's advisor → autopilot → digest does not run;
    - `/scheduler/status` keeps the earlier record.
  - **Why it matters:** this breaks AUD-084's invariant that "the tail must run regardless". The
    only writer writes integers, so the trigger needs a hand edit or a schema change.
  - **Fix here:** wrap that block. On an exception, log it and fall back to
    `summarize(..., previous=None)`, which cannot fail on the file. Add the review's probe R1 as
    a test.
- **I1 (info).** A symbol listed twice in the managed list, once `enabled: false`, is required and
  reviewed, and it also appears in `excluded`. Completion is not double-counted. The add API
  rejects duplicates, so only a hand edit produces it. Decide whether `excluded` should drop
  enabled symbols.
- **I2 (info).** With `RL_SCHEDULER_MAX_WORKERS` = 1 (production), reviews not yet started at a
  budget expiry read `failed: timeout`. They are then cancelled at `executor.shutdown`, so they
  never persist later, whereas a running straggler may. The count is right. Say which it was
  (`timeout` or `not started`) when the outcome vocabulary is unified.

See [the SA-004 review](../evidence/SA-004-review.md).

## Routed input — 2026-09-29 SA-007 review (F2, I1)

- **F2 (low, reproduced): one malformed SQLite file stops the whole nightly backup.**
  - **Where:** `services/data/backup.py`, `create_backup_archive`. `_snapshot_sqlite`,
    `sqlite_facts` and the `integrity != "ok"` gate raise, and nothing catches them per file.
  - **Example:** `atlas.db` is malformed and `transactions.jsonl` is healthy. Before SA-007 the
    archive held both files. Now the job raises `DatabaseError: database disk image is
    malformed`: no archive, no off-site copy and no `backup_status.json` are written. The ledgers
    stay unprotected every night until someone repairs the database. The job-error alert fires
    each night, and earlier archives are kept.
  - **Fix, with this story's `partial` outcome:** archive every other file, and record the bad
    database in the manifest as a failed entry. The job outcome and `backup_recoverable` then
    name it. Decide whether such an archive may go off-site. SA-007's D3 blocks it today.
    D4's argument ("a faithful copy of what is on the volume") suggests it should go.
- **I1 (info): local rotation ignores the drill.** `prune_backups` keeps the newest 7 archives
  whether or not they passed. With no bucket configured (production today), 7 failed-drill
  nights in a row would delete every good local archive. Each of those nights raises a job error
  and a watchdog warning. Consider never pruning the newest archive that passed its drill.

See [the SA-007 review](../evidence/SA-007-review.md) (probe P2).
