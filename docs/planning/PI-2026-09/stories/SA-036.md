# SA-036 — Record durable outcomes for every critical job

Priority: **P1** · Sprint: **1** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: none. Evidence: §2.3(3) in the [2026-09-23 production assurance review](../../../audit/2026-09-23-production-assurance-review.md). Added 2026-09-23 at the user's request.

## Intended result

Only `ipo_deep_dive` and `daily_review` call `record_job_outcome`. The brief, digests, autopilot, backup, watchdog and IPO refresh leave only logs, and those go with each deployment. "Did the 08:50 brief run?" has no durable answer.

Record an outcome for every scheduled job and expose them in the scheduler status.

## Starting points

- `services/scheduler/python/scheduler.py`
- `services/data/stores/job_outcomes.py`
- `services/api/routes/scheduler_api.py`

Paths are starting points; inspect current callers before editing. Keep this task bounded. If the implementation cannot fit a focused review, record a split with acceptance criteria in STATE.json before taking on another scope.

## Acceptance criteria

- Every scheduled job records started/finished time, status, counts and an error class.
- A job that raises still records `failed`; a failed outcome write never breaks the job.
- `GET /scheduler/status` shows every job's last outcome.
- An inventory test fails if any registered job id has no outcome wiring.

## Unit and integration evidence

- A test per job wrapper, including a crashing job.
- The 24-job inventory check proves coverage.
- The outcome file survives a simulated restart.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.
