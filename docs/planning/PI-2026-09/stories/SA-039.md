# SA-039 — Contain adaptive learning: observe-only, live weights back to defaults

Priority: **P0** · Sprint: **1** · Provisional estimate: **3 points**

Evidence: F02, F04 in the [September audit](../../../audit/2026-09-10-repository-production-review.md); §2.2 "Learning loop" and N8 in the [2026-09-23 production assurance review](../../../audit/2026-09-23-production-assurance-review.md). ## Intended result

The daily review adapts per-ticker agent weights on a target the September audit found wrong. Under F02, a price that rises from 100 to 103 against a forecast of 108 is classified DOWN, so a BUY is marked a miss. On 2026-09-23, production logged the `technical` weight at **0.0 for 5 of 6 observed tickers**, against its 0.12 default in the generic graph. For most tickers, chart signals currently carry no weight in the composite because of a mislabelled reward.

Add one named switch with two modes: `adapt`, which is today's behaviour, and `observe`. In `observe` mode:

- Every **decision** consumer of learned weights aggregates with the sector's configured default weights. These are the weights a ticker with no learning state gets today (the orchestrator's `_get_default_weights` / `get_sector_weights`). Do not use `WeightMemory.base_weights`, because the two initialisers disagree (see the note below).
- The stored `WeightMemory` is **not mutated**. The adapter still computes, and its would-be weights and deltas are recorded as a diagnostic with the mode, the reason and the review date.
- Tagged-lesson emphasis no longer moves agent scores in forecasts or re-forecasts. Lessons are still recorded.

Example: a ticker stores `technical = 0.0` at weight version v41. In `observe` mode its forecast uses `technical = 0.12`. After tonight's review the file still says 0.0 at v41. The diagnostic records what the adapter would have done.

This resets the live weights to the defaults, as the owner decided, without rewriting any weight file. Reading defaults instead of rewriting files needs no production data migration, keeps the learned history intact for forensics, and makes rollback exact: switching back to `adapt` resumes the stored weights unchanged.

**Code note (inspection, not verified in production):** `daily_review.py` initialises missing weight memory from `settings.AGENT_WEIGHTS` (the automobile table). `generate_forecast.py` initialises it from `get_sector_weights(sector)`. A file's `base_weights` may therefore come from another sector's table, which is why the default here is the sector table.

## Acceptance criteria

- In `observe` mode, for a ticker whose stored weights differ from the defaults, forecast generation, public analysis, and the review's re-scoring and re-forecast all aggregate with the sector defaults.
- In `observe` mode, a full daily review leaves `current_weights`, `weight_version` and `weight_history` unchanged. It writes one diagnostic record carrying the would-be weights and deltas, the mode, the reason and the review date.
- In `observe` mode, lesson emphasis leaves agent scores unchanged, and lesson recording continues.
- `adapt` mode behaves exactly as today: existing tests pass, and one test pins that `adapt` still writes weights.
- An unrecognised switch value fails closed to `observe` and logs a warning.
- The mode appears in the review's log line, in one read-only surface (for example the RL monitor or `/scheduler/status`), and in KT §5.
- The paper lane and the absurd-error path are unchanged.

## Unit and integration evidence

- Weights actually used in each mode: a fixture store whose learned weights diverge from the defaults. Compute the expected composite **by hand from the default table**, not from the implementation.
- A full review in `observe` mode with transports blocked: the weight file's hash is identical before and after, and the diagnostic record is present.
- Lesson emphasis is a no-op in `observe` mode.
- A non-automobile sector (the generic graph, `technical` 0.12) resolves its own defaults.
- Rollback: switching back to `adapt` resumes the stored weights byte for byte.

## Rollout and rollback

The implementation ships with `adapt` as the default, so its tests and review change no behaviour. **Activation** is a separate one-line commit that sets `observe` in the configuration. It is pushed only with the owner's explicit go-ahead, in a safe push window (every push redeploys), and may travel in the same push as the reviewed code.

Production verification happens after activation, through read-only probes that the owner runs:

- The next scheduled review logs `observe` mode.
- For sampled tickers, `weight_version` does not change across two reviews.
- The diagnostic records land.

Do not use the verdict-shadow `learned_weights_used` field as evidence. It is `bool(weights passed)`, and the orchestrator passes defaults when nothing is learned (`base_orchestrator.py` L149 → `signal_aggregator.py` L205), so it reads true in both modes. `learning_evidence.py` L414 counts it. Route that discrepancy to SA-024 rather than fixing it here. Do not trigger a job manually. Rollback is setting `adapt`, after which the stored weights resume exactly.

**Leaving `observe` mode** is an owner decision, taken only after SA-012 to SA-016 are accepted. SA-022 can use this switch's frozen default policy as its control. Also decide then whether `adapt` resumes from the stored weights or restarts from the defaults, since the stored values were learned on the defective target.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
