# SA-041 — Provide a read-only production status fetcher

Priority: **P1** · Sprint: **2** · Provisional estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: SA-036, SA-040. Design: §5.3 of the [production observability design](../../../superpowers/specs/2026-09-24-production-observability-design.md). Added 2026-09-24 at the owner's request (decision D5).

## Intended result

Today, "is production healthy?" is answered in one of three ways:

- the owner runs an ad-hoc probe through `railway ssh`;
- someone reads deployment logs, which are lost at each redeploy;
- the owner waits for an email that may not arrive.

On 2026-09-24 Claude could confirm the 08:00 IPO refresh only from log lines. Whether VARMORA's rows had actually landed on the volume could not be confirmed that way.

Add one read-only endpoint, `GET /ops/status`, and a command-line fetcher, `scripts/ops/fetch_status.py`. They give a sanitized verdict with its evidence, usable by the owner, by Claude in any session, or by a scheduled agent.

Example CLI output (illustrative):

```
StockAgent ops status — 2026-09-24 17:50 IST — deploy d9c459ae @ e8df088 — AMBER
 jobs     ipo_refresh_pm 17:45 ok (ladders 3/3) · rl_daily_review 16:30 ok (18 runs)
 sources  nse.bid_ladder 8/8 today · openrouter 131/131 today · smtp 1/1
 fresh    VARMORA captured 17:45 (0.1 h)
 budget   openrouter ~25 d at $0.40/d (key limit)
 alerts   none open
```

## Acceptance criteria

- **Auth.** The route accepts an `X-Ops-Token` equal to `OPS_READ_TOKEN` (constant-time compare), or an owner session. It **rejects `SCHEDULER_KEY`** and member sessions. With `OPS_READ_TOKEN` unset, token access is **closed**; this deliberately differs from `SCHEDULER_KEY`'s open-when-unset behaviour.
- **Read-only.** No store is written and no job is triggered; a test asserts no file or database changes.
- **Payload** (versioned schema):
  - deploy id and commit;
  - the verdict;
  - jobs: last run against the expected run, from SA-036;
  - sources and new signatures, from SA-040;
  - freshness: the newest IPO capture per open issue, the EOD cache and the latest brief date;
  - budgets: SA-035 readings, or `unknown`, never `$0`;
  - open watchdog alerts.
- **Verdict.** **RED** if a critical job is missed or failed today, a source is at 0% over at least N attempts, or runway is under 2 days. **AMBER** if something is stale, partial, or under a warning threshold. Otherwise **GREEN**. Thresholds come from `config.yaml`, and every RED or AMBER line carries its evidence.
- **Sanitization.** No user ids, emails, prompt text, raw log lines or secrets. Rate-limited.
- **CLI.** Reads `OPS_BASE_URL` and `OPS_READ_TOKEN` from the environment and prints the summary, or JSON with `--json`. It exits 0/1/2 for green/amber/red, with a network timeout, and never prints the token.
- **Witness.** When the SA-042 witness is enabled, the 06:30 watchdog pings `ops_status_green` only if the verdict is not RED.
- **Documentation.** KT §10 describes the endpoint. A runbook replaces the `railway ssh` probe routine, and HANDOFF says how to run it.

## Unit and integration evidence

- Auth matrix via TestClient: none, wrong token, right token, `SCHEDULER_KEY`, owner session and member session. Token unset means closed.
- Verdict fixtures from the design's §6 replays: each reaches its expected colour. The quiet twins stay GREEN.
- A sanitization fixture seeded with emails, user ids, prompt text and tokens: none appear in the payload.
- The CLI against a stub server: correct exit codes, and the token never appears in stdout or stderr.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Hard review

Can it report GREEN while a critical job was missed today? Can an anonymous caller learn anything? Can the unset-token state ever be open? Does the payload stay small and cheap under repeated calls?

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Activation needs `OPS_READ_TOKEN` set in Railway, which is a production variable change and needs the owner's authorization. The same token goes into the owner's local environment, never into the repository. Rollback: unset the token (the route closes) or disable `ops.status_enabled`.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
