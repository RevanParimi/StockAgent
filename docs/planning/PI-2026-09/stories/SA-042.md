# SA-042 — Add an outside witness for missed jobs (Healthchecks.io → Telegram)

Priority: **P1** · Sprint: **1** · Provisional estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not this card. Dependencies: SA-036. Design: §5.4 of the [production observability design](../../../superpowers/specs/2026-09-24-production-observability-design.md). Owner decisions 2026-09-24: D1 (Healthchecks.io, free tier) and D2 (Telegram).

## Intended result

The watchdog lives inside the app. Its only proof of life is a Sunday **email** heartbeat. From 16 Jul to 21 Sep, SMTP failed on every send, so by the code that heartbeat could not have arrived for about nine Sundays, and nobody noticed it was missing. On 22 Sep, a deploy that came up at 19:02 silently skipped the 19:00 `ipo_deep_dive`. Nothing inside a container can report that the container, its scheduler or its alert path is gone.

Add an outside witness. Each critical job checks in with Healthchecks.io, and when a check-in is missing or reports failure, Healthchecks.io messages the owner on Telegram. That path is independent of Gmail/SMTP, web push and Railway.

Example: on 22 Sep, the `ipo_deep_dive` check (cron `0 19 * * *`, `Asia/Kolkata`, 30-minute grace) receives no ping, and at 19:30 Telegram shows "ipo_deep_dive is DOWN". On 23 Sep, the 17:45 IPO refresh sends `/fail` with `partial:ladders 0/5`, and the message arrives within a minute.

## Acceptance criteria

- A ping helper sends `start`, success or `fail`, with a status word of at most 100 characters. It runs on a daemon thread with a 3 s timeout, never retries inline, never raises, and never delays the job.
- The payload holds only the check slug and the status word. It never carries user data, tickers from a user's portfolio, or secrets.
- The job-to-slug mapping lives in `config.yaml` under `ops.witness.checks`, starting with:
  - `ops_watchdog`, `ipo_refresh_am`, `ipo_refresh_pm`, `morning_brief` and `rl_daily_review`;
  - `ipo_deep_dive`, `bhavcopy_daily_sync`, `data_backup_nightly`, `audit_nightly` and `weekly_review`.

  An inventory test fails if a slug names no registered job.
- SA-036 status maps as follows. `ok` sends a success ping. `partial` and `failed` send `fail` with the reason word. `skipped_by_gate` sends a success ping saying `skipped:gate`, so a deliberately disabled job does not page.
- With `HC_PING_KEY` unset, the witness is off. No network call is attempted, and this is the default in tests and local runs.
- A runbook, stored with the ops documentation and linked from HANDOFF, covers:
  - creating the account;
  - adding the Telegram integration;
  - creating each check with its cron, the `Asia/Kolkata` timezone and a grace period;
  - where to set `HC_PING_KEY`;
  - how to pause a check during planned maintenance.

## Unit and integration evidence

- A fake transport exercises success, fail, timeout and unreachable. The job result is identical in all four.
- A crashing job sends `fail`. A job gated off sends `skipped:gate`.
- The key unset: the blocked-transport harness proves no connection was attempted.
- Payload assertion: only the slug and the status word leave the process.

Use deterministic fixtures and blocked external transports. Record exact commands, environment, results and any unsupported platform in the evidence receipt. Relevant existing tests plus these independent invariants are required; do not merely assert current implementation outputs.

## Rollout and rollback

**Owner actions**, not Claude's: create the Healthchecks.io account, connect Telegram, and set `HC_PING_KEY` in Railway. That is a production variable change needing the owner's authorization. Production verification uses Healthchecks.io's own "send test notification" to prove the Telegram path, then one real day of check-ins. Never stop a production job to test it. Rollback: unset `HC_PING_KEY`.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
