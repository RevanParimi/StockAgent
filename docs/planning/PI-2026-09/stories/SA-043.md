## Intended result

SA-039's `observe` mode keeps decisions on the default weights. It does not yet simulate a learner: each night the adapter starts again from the same frozen weight file (v41 → v42, and the next night v41 → v42 again). Its proposals never accumulate, so nothing can be measured over time. The stored learned weights cannot serve either. For example, `technical` was 0.0 for 5 of the 6 tickers that have it, against defaults of 0.12 and 0.10, because those weights were learned on the grading target the audit found wrong (F02).

Per-ticker learning is also statistically hopeless. It fits 6–9 weights from about 20 graded rows a month, about 2–3 rows per weight. Pooled across about 20 tickers, 6 factor weights get about 420 rows a month, about 70 per weight (the design's §4.5).

This story adds a **shadow learner**: one pooled table of six factor weights that learns every review day but never decides anything.

- **Shadow weights.** A single file, for example `data/rl/shadow_factor_weights.json`, starts from the **equal default table** (1/6 each), never from any stored per-ticker weights. It records an `evidence_start` date: the later of SA-015 and SA-045 going live. After each review day it applies **one** pooled update from that day's matured outcomes, in a deterministic ticker order, using SA-015's idempotent, bounded update path. Decisions are unaffected, and every per-ticker `WeightMemory` file stays untouched (the SA-039 invariant).
- **Paired decisions.** For each frozen decision (SA-014's issue-time record), the composite and verdict are computed twice from the **same SA-045 factor scores**: once with the default weights and once with the shadow weights in force at issue time. Both are stored with the decision ID, the issue cutoff and the shadow version. When the outcome matures, both are graded with SA-012's target. No extra LLM call is needed, because only the weighting differs.

Worked example (six factors; BUY starts at composite 0.55). Every factor scores 0.5 except Momentum at 0.78, so the composite is 0.5 + 0.28 × w_momentum. With the default weight 1/6 the composite is 0.547, which is NEUTRAL. The shadow has learned Momentum 0.25, which gives 0.570, a BUY. The two policies **disagree**. If the price then beats the target's threshold, the shadow was right on that decision. Decisions on which both policies agree carry no comparative information, so SA-022 scores only the disagreements.

The shadow works on the factor scores, which exist from SA-045 onward, so it does not wait for SA-047's engine switch. After a promotion (SA-022), the pair is the defaults against the live pooled table, which gives the reverse tally. The paper lane stays isolated: it adds no learning rows and no pairs.

## Acceptance criteria

- A review day advances only the pooled shadow file. Every per-ticker weight file is byte-identical, and live decisions are unchanged.
- The first shadow file equals the equal factor table (1/6 each) at version 0, with `evidence_start` set. No stored per-ticker or per-graph weights are ever copied into it.
- The same matured outcome contributes to the shadow at most once, including on retry and when one ticker's review is re-run (SA-015's checkpoint).
- Each paired record uses identical SA-045 factor scores for both policies. The shadow weights used are the version in force at the issue cutoff, so no update from that decision's own outcome, or any later one, is used.
- After a promotion, the pair is the defaults against the live pooled table.
- The paper lane and the absurd-error path add no learning rows and no pairs.
- The RL monitor shows the shadow version and weights and the number of pairs to date. This story adds no scorecard and no promotion.
- Rollback: disabling the shadow, or deleting its files, changes no decision.

## Unit and integration evidence

- The worked example above, computed by hand from the equal table and the configured thresholds: default NEUTRAL (0.547), shadow BUY (0.570).
- A three-review-day sequence: the shadow reaches v3, and every per-ticker weight file's hash is unchanged.
- A retry of the same date, and a re-run of one ticker: the shadow version and weights are unchanged.
- No look-ahead: a decision issued before review day N pairs with the shadow at version N−1, not N.
- Pooling: outcomes from two lenses both move the one table, and the order of tickers within a day does not change the result.
- The shadow never reads a per-ticker `WeightMemory` or a per-graph default table (see the L2 note on [SA-026](SA-026.md)).
- Paper lane: no shadow file and no pairs.

## Hard review

A shadow that shares a file, an object or a cache with any live weight memory fails review. So does a pair computed from different factor scores, or with shadow weights that already include the decision's own outcome. So does a per-ticker shadow. The reviewer derives the example composites by hand.

Apply [REVIEW.md](../REVIEW.md) in a fresh conversation after implementation. No unresolved critical/high defect may be signed off. If the reviewer changes behavior, return to implementation and retest; a self-review is not the fresh-session review.

## Rollout and rollback

Deploy as early as dependencies allow. SA-022's gates need about three months of shadow evidence, and that clock starts only at `evidence_start`, after SA-012 to SA-015 and SA-045 are live. Records from before `evidence_start` never count. Nothing here changes a decision, so rollback is disabling the shadow. Promoting the shadow's weights to live is SA-022's decision and a separate owner-authorized migration.

Local implementation completion and production verification are separate. Read-only inspection is authorized; this card does not authorize sending notifications, deploying, changing production variables, enabling policies, or applying destructive migrations.
